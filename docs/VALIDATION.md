# Validation and Reproducibility

## Status

The repository has been validated as an offline research prototype with deterministic synthetic inputs. This validation establishes software behavior under the tested cases; it does not establish clinical efficacy, sensor compatibility, or hard-real-time performance.

## Synthetic-input policy

All test physiology is generated by `tests/synthetic.py`:

- fixed, reproducible random seeds;
- mathematical EDA drift/noise;
- mathematical RR distributions;
- optional injected NaN gaps, motion, and contact-quality failures;
- no downloaded, captured, imported, or inferred participant data.

All session files in tests and `demo.py` are created under `tempfile.TemporaryDirectory`. They are removed automatically. The repository `.gitignore` also excludes `data/`, caches, virtual environments, and build products.

## Covered behaviors

The test suite covers:

- finite EDA/HRV feature extraction;
- small and excessive EDA missing-data paths;
- sampling-rate and configuration rejection;
- strict baseline readiness and unusable calibration rejection;
- extreme Z-score numerical stability;
- Kalman process-scale validation;
- multimodal confidence;
- posterior uncertainty growth during signal loss;
- uncertainty-based PI derating and hard-limit hold behavior;
- adaptive ISO acceleration, slowdown, reliability freeze, and monotonic floor behavior;
- adaptive trajectory/control telemetry in isolated end-to-end records;
- PI deadband and invalid timing;
- reversible layer changes and clock jitter;
- cancellation of stale pending commands;
- calibration/treatment-dose isolation;
- fast/slow cadence enforcement;
- cross-domain event monotonicity;
- end-to-end closed-loop operation and atomic records;
- idempotent completion and lifecycle rejection;
- safety abort and no-dose behavior;
- ISI futility evaluation;
- SHAM trajectory requirements, playback, and actual-parameter recording;
- dose upper bounds and research-arm distinctions;
- forty minutes of bounded synthetic closed-loop execution.

## Not validated

- Any clinical population, diagnosis, indication, outcome, or effect size.
- Accuracy against a reference EDA/ECG system.
- Robustness to all device artifacts or arrhythmias.
- Audio quality, psychoacoustic acceptability, or music-provider behavior.
- End-to-end latency, jitter, scheduling deadlines, or clock synchronization on production hardware.
- Security, privacy, availability, scalability, or disaster recovery.
- Regulatory compliance or medical-device software classification.

## Adding validation evidence

Keep generated evidence separate from source code:

1. Add deterministic tests under `tests/`.
2. Identify generated fixtures as synthetic in their module and test docstrings.
3. Write outputs to temporary directories.
4. Record software and dependency versions.
5. Separate software correctness, signal validity, usability, and clinical evidence.
6. Never commit participant data or credentials.

Real-data validation should use an approved protocol, consent and governance controls, a separate protected dataset, blinded analysis where appropriate, and a reproducible report that does not expose participant records.
